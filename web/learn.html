1Game trees

In any chess position the side to move has a list of legal moves (20 at the start, around 35 in a typical middlegame). Each move leads to a new position, where the opponent has its own list of moves, and so on. Drawn out, this is a game tree:

  • the root is the current position;
  • each branch is a move; each node is the position it leads to;
  • one level down is one ply (a half-move: one side moves);
  • the leaves are where we stop looking and judge the position with the evaluation function.

The tree grows very fast. With about 35 moves per position, looking d plies ahead means about 35d leaves:

Depth (plies)Leaf positions (≈ 35d)At 15,000 positions/s

This is why a chess program cannot simply look at everything, and why the clever parts of this project (alpha-beta and pruning) matter so much.

2Minimax

Two players take turns. The AI is MAX: it wants the score as high as possible. The opponent is MIN: it wants the score as low as possible. Minimax assumes both play their best:

minimax(position, depth, maximizing):
    if depth == 0 or game over:
        return evaluate(position)
    if maximizing:                                  # AI's turn
        return max(minimax(child, depth-1, False) for each move)
    else:                                           # opponent's turn
        return min(minimax(child, depth-1, True)  for each move)

Below is a small tree: ▲ MAX nodes, ▼ MIN nodes, and ■ leaves with their evaluation scores. Press Step to follow minimax, or Play to animate it. Values travel up from the leaves: MIN nodes take the lowest child value, MAX nodes the highest.

Minimax visits every leaf. The answer is correct, but the cost grows as bd (b = moves per position, d = depth).

3Alpha-beta pruning

Alpha-beta gives exactly the same answer as minimax, but skips branches that cannot change it. It carries two numbers down the tree:

  • α (alpha): the best score the AI (MAX) is already guaranteed somewhere else;
  • β (beta): the best score the opponent (MIN) is already guaranteed somewhere else.

If a position becomes so good for one side that the other side would simply avoid it (α ≥ β), the remaining moves there do not matter. That is a cutoff: the rest of that branch is pruned.

alphabeta(position, depth, α, β, maximizing):
    if depth == 0 or game over: return evaluate(position)
    if maximizing:
        value = -∞
        for each move:
            value = max(value, alphabeta(child, depth-1, α, β, False))
            α = max(α, value)
            if α >= β: break        # β-cutoff: MIN will never allow this position
        return value
    else:
        value = +∞
        for each move:
            value = min(value, alphabeta(child, depth-1, α, β, True))
            β = min(β, value)
            if α >= β: break        # α-cutoff: MAX will never play into this position
        return value

Same tree as above. Watch α and β change, and the dashed branches that are never visited.

4Move ordering

Alpha-beta cuts off the most when the best move is tried first: then every other move only has to be shown "not better", which is quick. With the worst move first it saves almost nothing. Knuth & Moore (1975) showed that with perfect ordering alpha-beta needs only about b⌈d/2⌉ + b⌊d/2⌋ − 1 leaves instead of bd: it can search twice as deep in the same time.

The engine orders moves with cheap guesses: the best move from the previous search (from the transposition table), then captures (most valuable victim first), then killer moves (quiet moves that caused cutoffs nearby), then a history score.

6Quiescence search & the horizon effect

Stopping the search at a fixed depth has a trap. In this position White can take a pawn with the queen: Qxd5. If the search stops right after that move, the evaluation sees "White has won a pawn". But the pawn on d5 is defended: ...exd5 wins the queen. A search that stops too early does not see this, because it is beyond its horizon.

–

Quiescence search fixes this: when the planned depth runs out, the AI keeps searching captures only until the position is quiet. At each such node it may also "stand pat" (keep the static score) if no capture improves it. In the project tests, the engine without quiescence plays Qxd5 at depth 1 and the engine with it does not (test_quiescence_avoids_horizon_blunder).

7From textbook to engine

Negamax. The engine writes minimax in a shorter form. Every score is from the point of view of the side to move, and is negated when passed up the tree, because max(a, b) = −min(−a, −b). One function then plays both colours. The tests check it returns exactly the textbook minimax score.

Iterative deepening. The engine searches depth 1, then 2, then 3… until its time is up. There is always a finished answer, and each depth's best move is tried first in the next, which makes alpha-beta cut off more.

More pruning. On top of alpha-beta the engine uses a transposition table (remembers positions), principal variation search, null-move pruning, late-move reductions and futility pruning. Measured on this project (positions searched to depth 4, four test positions, from scripts/ablation.py):
